Ursula exposes a small public HTTP API for durable append-only streams. Most users only need the `/{bucket}/{stream}` route family, which maps cleanly to buckets and stream IDs.

This API is Ursula's implementation of the [Durable Streams Protocol](/docs/specs/durable-stream), defined by the durable-streams community, with additional route families for compatibility and deployment needs.

## Bucket operations

| Method | Path | Description |
| -------- | ----------------------------- | ------------------------------------------------------------ |
| `PUT` | `/{bucket}` | [Create a bucket](/docs/api/create-bucket) (validates the ID; buckets are implicit) |

There is no bucket metadata read, stream listing, or bucket delete. Removing a bucket is an operator action ([bucket purge](/docs/operations#tenant-offboarding-bucket-purge)), which permanently fences the bucket ID: later stream creates in it answer `404`.

## Stream operations

| Method | Path | Description |
| -------- | ----------------------------- | ------------------------------------------------------------ |
| `PUT` | `/{bucket}/{stream}` | [Create a stream](/docs/api/create-stream) |
| `POST` | `/{bucket}/{stream}` | [Append data or close](/docs/api/append) |
| `GET` | `/{bucket}/{stream}` | [Read (catch-up, long-poll, SSE)](/docs/api/read) |
| `HEAD` | `/{bucket}/{stream}` | [Get stream metadata](/docs/api/head-stream) |
| `DELETE` | `/{bucket}/{stream}` | [Delete a stream](/docs/api/delete-stream) |

## Bootstrap and snapshots

| Method | Path | Description |
| -------- | --------------------------------------------- | ---------------------------------------------------- |
| `GET` | `/{bucket}/{stream}/bootstrap` | [Snapshot + tail replay](/docs/api/bootstrap) |
| `GET` | `/{bucket}/{stream}/snapshot/{offset}` | [Read snapshot at offset](/docs/api/read-snapshot) |
| `PUT` | `/{bucket}/{stream}/snapshot/{offset}` | [Publish a snapshot](/docs/api/publish-snapshot) |

## Common request patterns

### Create a bucket and stream

```bash
curl -X PUT http://127.0.0.1:4437/demo
curl -X PUT http://127.0.0.1:4437/demo/hello
```

### Append data

```bash
curl -X POST http://127.0.0.1:4437/demo/hello \
  -H 'Content-Type: application/octet-stream' \
  --data-binary 'hello world'
```

### Read from the beginning

```bash
curl 'http://127.0.0.1:4437/demo/hello?offset=-1'
```

### Subscribe with SSE

```bash
curl 'http://127.0.0.1:4437/demo/hello?offset=-1&live=sse'
```

## Refusals that applied nothing

A client may count a write attempt as never applied, which means that nothing of it can apply later, only when the response

- has the status `401`, `402` or `429`, or
- carries both `x-ursula-not-applied` and `x-ursula-not-applied-checked`. Only a gateway at 0.7.3 or newer sends the second header.

Any other response proves nothing, including a `403`, `413` or `503` without both headers. A `503` without them, or a timeout, can follow a write that committed. After such an attempt, keep retrying with the same `Producer-Id`, `Producer-Epoch` and `Producer-Seq` until an answer settles the write, so that the server deduplicates it (see [exactly-once writes](/docs/concepts/exactly-once-writes)).

`x-ursula-not-applied`, the marker, answers a request that was refused before anything of it was proposed, so nothing of it can apply later. Its value is a short token that names the refusal, such as `RaftLogPressure`. Log the token, but rely only on the presence of the header. `x-ursula-not-applied-checked: 1`, the vouch, comes only from a gateway at 0.7.3 or newer, which sets it on every response it returns after it applied the redirect rule below. Nodes never set the vouch, so a client that talks to the nodes directly ignores the marker.

The three statuses count without the headers. A layer in front of the nodes, such as the gateway's access control and tenant limits, answers them before it forwards a request. The server never answers `401` or `402`, and answers `429` only to a new producer on a stream that has no room for one. That refusal applies nothing, and a replay of a write that did commit would be deduplicated instead.

The server sets the marker on every refusal of its write admission, which runs before a request reaches the stream:

| Status | Token | Cause |
| ------ | ----- | ----- |
| `503` | `WalDiskPressure` | The WAL filesystem's free space is below `raft.wal.min_available_size`, or the free-space check failed. Writes pass again once the free space reaches `raft.wal.resume_available_size`. |
| `503` | `RaftLogPressure` | The node's unsnapshotted Raft log is over twice `raft.snapshot_log_budget`. Writes with a body pass again once the log is below 1.5 times the budget. Writes without a body still pass. |
| `503` | `IngressBodyBytesLimitReached` | Write bodies in flight on the node leave too little of `server.http_inflight_body_size` for this body. |
| `413` | `RequestBodyTooLarge` | The `Content-Length` is over the route's limit. |

The `503` refusals also carry `Retry-After: 1` and name the token as the JSON `error`.

The gateway sets the marker on every request it refuses before forwarding it, and on a request it could not send because the connection to its first upstream failed. It passes a node's marker through, except after a leader redirect, as described below. Its tokens are listed in the [gateway README](https://github.com/tonbo-io/ursula/blob/main/crates/ursula-gateway/README.md#refusals-that-applied-nothing). A proxy in front of the gateway can make its own refusals count too: answer them with `401`, `402` or `429`, or set both headers, but only on requests it did not pass on.

The marker speaks for one attempt only. A marked answer to a retry says nothing about the earlier attempts.

### Redirects and retries

A node can answer a write with a leader redirect after it proposed the write. The gateway follows Raft leader redirects itself and keeps the leader's marker only if the redirect carried one too. Gateways older than 0.7.3 pass the leader's marker on after any redirect, but they never send the vouch, so a client that requires the vouch does not trust their markers. Upgrading gateways before nodes, and rolling back nodes before gateways, is still recommended, so that clients keep the benefit of the marker during a rollout. But no order, including whichever order a `helm upgrade` or `helm rollback` replaces gateways and voters in, can make a client count a committed write as never applied.

An HTTP library or proxy that follows redirects or retries a write on its own hides the earlier attempts, and the vouch covers only the one request the gateway received. Turn both off for writes before relying on the marker. Checking for a followed redirect, such as a `fetch` response whose `redirected` is `true`, is not enough, because a retry leaves no such trace. A proxy in front of the gateway must not retry writes. With ingress-nginx, set `nginx.ingress.kubernetes.io/proxy-next-upstream: "off"`, as the chart's [TLS ingress example](https://github.com/tonbo-io/ursula/blob/main/charts/ursula/examples/tls-ingress.yaml) does.
