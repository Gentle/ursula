Ursula exposes a small public HTTP API for durable append-only streams. Most users only need the `/{bucket}/{stream}` route family, which maps cleanly to buckets and stream IDs.

This API is Ursula's implementation of the [Durable Streams Protocol](/docs/specs/durable-stream), defined by the durable-streams community, with additional route families for compatibility and deployment needs.

## Bucket operations

| Method | Path | Description |
| -------- | ----------------------------- | ------------------------------------------------------------ |
| `PUT` | `/{bucket}` | [Create a bucket](/docs/api/create-bucket) (validates the ID; buckets are implicit) |

There is no bucket metadata read, stream listing, or bucket delete. Removing a bucket is an operator action ([bucket purge](/docs/operations#tenant-offboarding-bucket-purge)), which permanently fences the bucket ID: later stream creates in it answer `404`.

## Stream operations

| Method | Path | Description |
| -------- | ----------------------------- | ------------------------------------------------------------ |
| `PUT` | `/{bucket}/{stream}` | [Create a stream](/docs/api/create-stream) |
| `POST` | `/{bucket}/{stream}` | [Append data or close](/docs/api/append) |
| `GET` | `/{bucket}/{stream}` | [Read (catch-up, long-poll, SSE)](/docs/api/read) |
| `HEAD` | `/{bucket}/{stream}` | [Get stream metadata](/docs/api/head-stream) |
| `DELETE` | `/{bucket}/{stream}` | [Delete a stream](/docs/api/delete-stream) |

## Bootstrap and snapshots

| Method | Path | Description |
| -------- | --------------------------------------------- | ---------------------------------------------------- |
| `GET` | `/{bucket}/{stream}/bootstrap` | [Snapshot + tail replay](/docs/api/bootstrap) |
| `GET` | `/{bucket}/{stream}/snapshot/{offset}` | [Read snapshot at offset](/docs/api/read-snapshot) |
| `PUT` | `/{bucket}/{stream}/snapshot/{offset}` | [Publish a snapshot](/docs/api/publish-snapshot) |

## Common request patterns

### Create a bucket and stream

```bash
curl -X PUT http://127.0.0.1:4437/demo
curl -X PUT http://127.0.0.1:4437/demo/hello
```

### Append data

```bash
curl -X POST http://127.0.0.1:4437/demo/hello \
  -H 'Content-Type: application/octet-stream' \
  --data-binary 'hello world'
```

### Read from the beginning

```bash
curl 'http://127.0.0.1:4437/demo/hello?offset=-1'
```

### Subscribe with SSE

```bash
curl 'http://127.0.0.1:4437/demo/hello?offset=-1&live=sse'
```

## Refusals that applied nothing

A response with the `x-ursula-not-applied` header answers a request that was refused before it reached the stream. Nothing of the request was applied, whatever the status. The value is a short token that names the refusal, such as `RaftLogPressure`. Log the token, but rely only on the presence of the header.

The server sets the header on every refusal of its write admission, which runs before a request reaches the stream:

| Status | Token | Cause |
| ------ | ----- | ----- |
| `503` | `WalDiskPressure` | The WAL filesystem's free space is below `raft.wal.min_available_size`. Writes pass again once it reaches `raft.wal.resume_available_size`. |
| `503` | `RaftLogPressure` | The node's unsnapshotted Raft log is over twice `raft.snapshot_log_budget`. Writes with a body pass again once the log is below 1.5 times the budget. Writes without a body still pass. |
| `503` | `IngressBodyBytesLimitReached` | Write bodies in flight on the node leave too little of `server.http_inflight_body_size` for this body. |
| `413` | `RequestBodyTooLarge` | The `Content-Length` is over the route's limit. |

The `503` refusals also carry `Retry-After: 1` and name the token as the JSON `error`.

The gateway sets the header on every request it refuses before forwarding it, and passes an upstream's header through. Its tokens are listed in the [gateway README](https://github.com/tonbo-io/ursula/blob/main/crates/ursula-gateway/README.md#refusals-that-applied-nothing). A proxy in front of Ursula may set the header too, but only on requests it refused without passing them on.

The header speaks for one attempt only. A marked answer to a retry says nothing about the earlier attempts. Without the header a response promises nothing. A `503` without it, or a timeout, can follow a write that committed. After such an attempt, keep retrying with the same `Producer-Id`, `Producer-Epoch` and `Producer-Seq` until an answer settles the write, so that the server deduplicates it (see [exactly-once writes](/docs/concepts/exactly-once-writes)).

### Redirects and retries

A node can answer a write with a leader redirect after it proposed the write. A client that follows redirects keeps the header of the final response only if every redirect it followed carried the header too. The gateway follows Raft leader redirects this way. A gateway older than 0.7.3 passes the leader's header on after any redirect. Upgrade gateways before nodes, and roll back nodes before gateways, so that no older gateway runs in front of a node that sets the header.

An HTTP library or proxy that follows redirects or retries on its own hides the earlier attempts. Turn that off for writes before relying on the header, or ignore the header on a response that followed a redirect, such as a `fetch` response whose `redirected` is `true`. A proxy that sends one request upstream more than once passes the header on only if every attempt carried it.
